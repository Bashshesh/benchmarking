# Measurement methodologies and their boundaries

4 November 2026. A **metric** is the quantity, a **technique** is how it is observed, an **experimental design** allocates controlled observations, and an **analysis** summarizes/infers from them. They are not interchangeable. This document describes implemented support; actual execution status and evidence paths are consolidated in UPGRADE_RESULTS. Published evidence is separately audited in RESEARCH_METHODS_AND_EVIDENCE.

| Method and category | Research question and quantity | Assumptions and overhead | Applicability, strengths and limitations | Project evidence route |
|---|---|---|---|---|
| Internal elapsed time, metric + monotonic timer technique | How long does the defined operation take? | Timer boundaries/correctness must be trusted; startup excluded. Calls/loops not independent samples. | Portable Python/Java; reflects waiting/scheduling as well as work. No end-to-end application claim. | Existing runner, unchanged 17-case baseline; MetricsBench; measured redundant-work grid. |
| Whole-process elapsed time, metric | What does startup/setup plus work cost? | Includes process/JVM imports, wrapper/job and source-check overhead. | Useful for startup-sensitive use cases; must compare identical harness/boundaries. Historical old/final/upgrade harnesses cannot be pooled. | Existing raw.csv process_seconds retained separately. |
| Process CPU time, metric + JVM management technique | Does optimization reduce CPU consumed, or only elapsed time? | JVM process total includes compiler/GC/background JVM threads, clock granularity; query overhead outside kernel timer but surrounding window differs slightly. | More informative about CPU tradeoffs than wall time alone; not energy or isolated application-thread work. Zero/tiny samples limit ratios. | MetricsBench process_cpu_seconds_per_operation; separate per-process payloads. |
| Throughput, metric | Operations completed per unit time? | Here inverse batch-average operation time, not an independent new workload or saturation study. | Explains engineering capacity for the exact operation; no request-level service throughput inference. | MetricsBench throughput_ops_per_second. |
| Median/p95/p99 operation latency, metrics + iteration tracing | Are individual operations variable or heavy-tailed? | Per-call timers perturb fast operations; within-process values correlated, tails require many observations and workload realism. | Diagnostic distribution on one JVM, not independent-fork tail inference or service SLA. | Separate latency diagnostic with raw nanoseconds and nearest-rank quantiles. |
| Per-thread allocated bytes, metric + ThreadMXBean technique | Does optimization allocate less in the observed thread window? | JDK support/enablement required; management/observer costs and thread scope; zero does not prove memory equivalence. | Allocation tradeoff, not retained heap/peak RSS or whole-JVM allocation. | MetricsBench allocation payload. |
| Peak RSS/heap, resource metrics | Does optimization increase peak/retained memory? | Sampling misses short peaks; JVM reservation != residency; external monitoring can perturb. | Not implemented as a trustworthy peak-memory measurement in this upgrade. Do not substitute ThreadMXBean allocation. | Explicitly unmeasured. |
| Sampling/differential profiling, technique | Which hot methods consume sampled CPU? | Sampling error, duration/operation-count normalization and instrumented-environment effects. | JFR execution samples provide hotspot evidence; raw count differences across unequal budgets are not speedups/causes. | Separate project-owned linear/binary JFR runs. Real Roaring profiling blocked. |
| JVM compilation/GC/JFR tracing, technique | Is code compiled at different tiers? Are GC/runtime events present? | Profile settings/thresholds affect visibility; no event does not prove absence. Diagnostic overhead must be separated. | Native JDK21 tools; compilation levels are not disassembly. Causal JIT isolation needs more controls. | JFR Compilation, GC, CPU/allocation samples; PrintCompilation and GC/safepoint logs. |
| CPU affinity/contention intervention, experimental design | Does controlled load/placement alter internal duration and variation? | Same CPU class/core topology required for narrower interpretation; cache/SMT/frequency/background factors remain. | Baseline quiet/sameCPU/separateCPU; native same-class mitigation separates one hybrid-class confound. | Existing baseline plus CPU-set topology and planned same-class pair. |
| CPU frequency/temperature/counters, diagnostic metrics | Does hardware state explain noise? | psutil frequency may be coarse/nominal/system-wide; no thermal sensor or hardware counter is invented. Privileged perf/PMU support absent. | Frequency/context-switch observations support hypotheses, not causal attribution to this workload. Thermal/perf counters remain unmeasured. | Read-only topology/probe metadata; no perf/thermal claims. |
| Startup vs finite-window warmup, experimental design | How sensitive is a configured window to initialization/adaptation? | Same number of discarded calls != equal duration or steady state. | Existing Java0/20 warmup; settings experiment records fixed policy. | Baseline and separate JFR; no steady-state claim. |
| JMH forked microbenchmark, technique/design | Can the same actual library operation be compared across commits? | Independent fork summaries, frozen fixture/harness/flags, correctness before timing; nested iterations not flattened. | Standard Java microbenchmark framework; broader application relevance still must be established. | External845 JMH1.37 harness prepared; all actual execution blocked by Docker. |
| Randomized paired rounds, experimental design | Reduce fixed arm-order confounding and retain local pairing? | Representative sufficiently independent rounds assumed; desktop drift remains. | Reuses original randomization/analyzer; same-host seeds are repeatability, not new machines. | All baseline/native pairs, exact order and seed retained. |
| Hierarchical design/analysis | Separate build/fork/iteration variance? | Requires sufficient replication at each level and declared estimand. | One-fork JMH adapter supports valid unit boundaries. No full multilevel variance model/build-level replication is claimed. | Adapter rejects multi-fork flattening; future hierarchical model. |
| Paired percentile bootstrap, statistical analysis | Relative mean-time effect and practical relevance? | Finite sample, independence/representativeness and approximate coverage; 5000 paired resamples. | Original ±5% four-outcome rule unchanged. No multiple-testing adjustment or universal coverage guarantee. | Exact original analyzer; synthetic operating-characteristic study and raw reanalysis. |
| Change-point analysis, statistical technique | Does a runtime enter stable phases? | Model/penalty choices, enough ordered iteration data and validated tools needed. | Not implemented from scratch. Barrett/Traini methods motivate retaining traces; lag-one/half-drift is not change-point detection. | Future validated changepoint tool; current descriptive diagnostics only. |

## Scientific rationale

Georges2007 motivates JVM invocation replication and startup separation; Kalibera/Jones2013 distinguishes nested sources of variability; Mytkowicz2009 and STABILIZER2013 show repetition alone cannot repair setup bias; Barrett2017 and the provisionally resolved Traini2023 caution against fixed-warmup/steady-state assumptions; Laaber/Leitner2018 cautions about benchmark sensitivity and representative workloads. Full identities, primary URLs, published quantitative findings and limits are in RESEARCH_METHODS_AND_EVIDENCE rather than copied as local evidence.

## Targets and additional metrics

No customer requirement or defensible external SLA was supplied for the synthetic search workload. Preserve the earlier 3ms graph budget as historical/illustrative only. The new runtime-setting question uses an explicit engineering goal fixed before execution: validate >5% faster internal operation time on a held-out run and do not recommend if observed mean process CPU rises >10%. This is a workload-specific experimental selection objective, not a service guarantee. If no setting meets it, retain default and report no supported configuration change. Additional CPU/allocation/throughput measures expose tradeoffs; none substitutes for end-to-end latency or energy.
