# PerfLens: focused literature and measurement rationale

Research question: **How can software performance be measured reliably, and which optimization techniques provide reproducible improvements?**

This is a focused selection of five primary studies, not a systematic review. Sources and linked project pages were checked on 29 October 2026. No benchmarks or replications were run for these notes. “Verified” below means that the linked page was readable and its identity/content matched; it does not mean its software was installed or its results reproduced.

## Methodological comparison

These papers address different failure modes. Georges et al. motivate uncertainty-aware Java evaluation; Kalibera and Jones make nested repetition economical; Mytkowicz et al. show why repetition alone does not remove systematic bias; Barrett et al. challenge the assumed execution phase being summarized; Laaber and Leitner examine whether a benchmark suite can detect relevant changes. They complement one another rather than identify one universally sufficient benchmark procedure. The links in the matrix support these characterizations.

## Proposed PerfLens protocol

The following is a project design derived from the evidence, **not a verbatim procedure jointly validated by these five papers**.

1. **Specify the claim first.** Choose elapsed time or throughput, workload/input sizes, timing boundaries, correctness conditions, and whether startup is included. Freeze source versions and record OS, hardware, runtime/compiler, flags, dependencies, and background-load conditions. Microbenchmark improvements require separate confirmation on a representative application workload before an application-level claim.
2. **Use fresh-process rounds.** Run each baseline and candidate in a fresh process in every round. Randomize their order within rounds using a saved seed. Preserve round identity. This reduces order confounding but does not establish independence: shared thermal state, caches, and background load can remain. Order randomization is also narrower than Mytkowicz et al.’s setup randomization; it does not resolve memory-layout bias.
3. **Make warmup observable.** Save within-process iteration timing sequences. Select any discard policy using pilot data, then freeze it before confirmation. A fixed discard is an operational convention, not evidence that a steady state was reached. If the trace remains unstable, describe the finite-window measurement and avoid calling it steady-state performance.
4. **Respect the independent sampling unit.** Reduce each process to a prespecified summary and estimate the ratio of candidate to baseline arithmetic mean time, R = mean(candidate) / mean(baseline). For paired rounds, bootstrap whole round pairs with replacement and recompute that ratio; do not bootstrap individual inner iterations as if independent. If executions are unpaired, resample independent process summaries separately. Save bootstrap seed, resample count, confidence level and method. A bootstrap interval assumes the sampled units adequately represent the target distribution; it does not repair drift or biased setup. This simplified ratio-of-means bootstrap is PerfLens’s analysis choice, not an assertion that the 2013 paper prescribes this exact implementation.
5. **Separate uncertainty from usefulness.** Prespecify a practical threshold, for example a minimum 5% reduction in elapsed time, as a project choice. With R defined above, a 95% interval entirely below 0.95 supports that threshold for the measured setting; an interval below 1 but overlapping 0.95 supports a detectable reduction without establishing the practical target. An interval containing 1 leaves the direction of change uncertain. If the entire interval lies within a prespecified practical tolerance, the practical decision can still be within_threshold; this is never proof that the implementations have identical performance. Do not adapt thresholds after seeing winners.
6. **Confirm once selection ends.** Use pilot runs for tuning and candidate selection. Freeze the chosen implementation and protocol, then collect held-out fresh-process rounds with new order seeds. Report all selected comparisons, including failures. Held-out confirmation reduces selection optimism; broader reproducibility requires additional machines, inputs, or independently recreated environments.

## What can be concluded about optimizations?

These five papers primarily justify **how to evaluate** optimization claims. They do not establish a universal ranking of caching, algorithm changes, allocation reduction, vectorization, or parallelization. PerfLens should treat each technique as a hypothesis: predict its mechanism, establish correctness, measure its cost and benefit under specified workloads, and confirm the selected change on held-out measurements. Record workload-specific regressions and tradeoffs alongside improvements. Until such measurements exist, any speedup is a hypothesis or literature result, never a PerfLens experimental finding.

## Technical note: original NumPy sorted-argsort workload

This historical case has direct support in the official project tracker. [NumPy issue #28714](https://github.com/numpy/numpy/issues/28714), opened 15 April 2025, reports `arr = np.arange(10**5)` followed by timed `arr.argsort()`: 444 microseconds for 1.26.4 and 1.59 milliseconds for 2.0 in the reporter's Python 3.12.3/Linux setting. These are the reporter's measurements, not PerfLens results. A NumPy member attributes the ordered-array slowdown, particularly for 64-bit dtypes, to the AVX2 argsort implementation introduced by PR #25610. That attribution is upstream evidence for a mechanism; a local release comparison alone does not establish it causally.

The [NumPy 2.0 release notes](https://numpy.org/doc/2.0/release/2.0.0-notes.html) document hardware-specific sorting acceleration and a Windows default-integer change from int32 to int64. Therefore preserve the original implicit-dtype workload for reproduction, record the actual dtype, and distinguish that historical workload comparison from an explicit fixed-dtype diagnostic. Record CPU capabilities and package builds as well. The release notes do not promise every input becomes faster.

The upstream [PR #28619](https://github.com/numpy/numpy/pull/28619), merged into main on 14 May 2025, explicitly includes a fix for sorted-data argsort regressions alongside other sorting changes. Its inclusion in any particular release was not checked here. Consequently the bounded claim is about pinned 1.26.4 versus 2.0.0, on the measured workload and environment; no conclusion about current NumPy versions or all sorting inputs follows. This source check ran no benchmarks.
